# Vibe Coding 做得出 Demo，Harness Engineering 才能交付

这两年，`vibe coding` 给了很多人一种前所未有的兴奋感。

以前需要产品、设计、前端、后端一起配合的事情，现在一个人带着几个 agent，几小时就能做出一个能跑的东西。这个变化是真的，而且很重要。

但很多人也因此得出了一个危险结论：既然 AI 已经会写代码了，软件生产的主要矛盾就解决了，工程师思维可以退场了。

我越来越确定，这个结论对 demo 成立，对商业化交付不成立。

`vibe coding` 最擅长的是把“无”快速变成“有”。它很适合做原型、页面、MVP、轻量工具，也适合把一个模糊想法迅速推到可见、可试、可讨论的状态。可一旦产品真的要接真实用户、真实数据、真实发布节奏，问题就会立刻换一个维度：状态怎么管，异常怎么兜，需求改动会不会牵一发动全身，线上出事谁来排查，版本回滚怎么做，下一轮 agent 进来还能不能接得住上下文。

这时候你会发现，真正拉开差距的，已经不是“AI 会不会写”，而是“你有没有一套让 AI 持续稳定出活的工程系统”。

这正是 `Harness Engineering` 在 2026 年突然变重要的原因。它不是一个比 `prompt engineering` 更时髦的新词，而是 AI 开发迟早都要补上的那笔工程账。

## `vibe coding` 的边界，不在写代码，在交付

如果只看生成速度，`vibe coding` 几乎是碾压式的。一个页面、一个后台、一个流程、一个小工具，AI 确实能把过去几天的工作压缩到几个小时。

可 demo 和交付，本来就不是一回事。

demo 的世界很宽容。需求边界还没定死，数据量不大，状态流转简单，失败成本也低，哪怕某个细节写得不够严密，只要看起来能跑，大家就愿意继续往前。

商业化交付完全不是这样。商业化意味着你要对结果负责，而不是只对“看起来差不多”负责。你要面对的是持续迭代、权限边界、真实数据、异常流程、发布节奏、回归验证和线上问题。你卖的不是一段代码，你卖的是一个在变化中仍然能工作的系统。

所以，`vibe coding` 真正的能力边界，从来不是“它能不能把代码写出来”，而是“它能不能在复杂约束里长期保持稳定”。

一句话说透就是：

> `vibe coding` 解决的是“先做出来”，`Harness Engineering` 解决的是“做出来以后别崩”。

## 我们做小程序时，其实已经在补 `Harness`

很多人把 `Harness Engineering` 当成 2026 年才冒出来的新概念。我不太这么看。

更准确的说法是：在 Anthropic 于 `2025-11-26` 发布 *Effective harnesses for long-running agents*、OpenAI 于 `2026-02-11` 发布 *Harness engineering: leveraging Codex in an agent-first world*、Martin Fowler 于 `2026-04-02` 发布 *Harness engineering for coding agent users* 之前后，这个问题其实已经在真实交付里存在了。只是那时候，大多数人还没有用一个统一的词把它讲清楚。

我们做小程序时，就已经被这个问题狠狠干过一遍。

AI 确实能很快帮我们把页面、组件、接口草稿、交互流程搭起来。用它做从 0 到 1 的启动，效率非常高。这一步我一点也不怀疑，甚至可以说，这是 AI 写代码最有价值的地方。

但只要开始接真实数据、接状态流转、接权限边界、接发布节奏，事情立刻就变了。你会发现自己开始补的，不再是“更强的 prompt”，而是一整套外层系统：

- 要把需求、页面、接口、状态说明写成文档，不然后续 agent 根本接不上上下文。
- 要把目录结构、组件边界、命名方式、接口契约定下来，不然每次重写都在破坏一致性。
- 要有检查点和自测清单，不然你根本不知道这次改动到底修好了还是又带出了新问题。
- 要有回归和回滚意识，不然一个看起来很小的改动，就可能把线上流程一起带崩。
- 要有明确的阶段拆分，不然 agent 会一直在错误上下文里越跑越偏。

回头看，这些动作本质上都不是“多会写一点代码”，而是“给 AI 搭一副能长期工作的马鞍”。

这就是为什么我现在更愿意把我们那套做法叫做“工程化的全栈 vibe coding”。我们不是比谁更早发明了 `Harness Engineering` 这个词，我们只是更早在真实交付里遇到了同一个问题，也更早被迫补上了同一类能力。

## 2026 年被重构的，不是 coding，而是生产范式

很多人理解 `Harness Engineering`，还停留在“给 agent 多接几个工具”。这其实只看到了表层。

它真正重构的，不是写代码这一个动作，而是整个生产范式。

过去大家比的是谁更会写 prompt。现在真正拉开差距的，是谁能把 agent 放进一套可规划、可执行、可验证、可回退的系统里。这个变化至少有四层：

- 生产单元变了。以前是“人和模型的一次对话”，现在是“人定义系统，多个 agent 在系统里分工推进”。
- 核心资产变了。以前最值钱的是 prompt，现在更值钱的是 repo 结构、文档体系、检查清单、状态记录、验证脚本和反馈回路。
- 质量标准变了。以前是“看起来像能用”，现在是“有没有证据证明它真的可交付、可回归、可维护”。
- 瓶颈位置变了。以前大家觉得瓶颈在生成能力，现在越来越清楚，真正的瓶颈在约束、上下文治理、错误恢复和交付责任。

这也是为什么我会说，2026 年 `Harness Engineering` 重构的，不是 `vibe coding` 的写法，而是 `vibe coding` 的生产范式。

AI 还是那个 AI，代码生成还是很快，但赢家不再是写得最快的人，而是能把速度组织成结果的人。

## AI 一人公司，最后还是要回到工程师思维

这里最容易被误解的一点是：我说“回到工程师思维”，不是说 AI 一人公司最后要退回传统大团队的那套流程，更不是说要否定 `vibe coding`。

恰恰相反，我非常认可 `vibe coding` 的价值。没有它，AI 一人公司这件事根本不可能成立。问题只在于，如果你真的想把它做成一门生意，只会“让 AI 帮你写”是不够的，你还得会“让 AI 在你的系统里稳定工作”。

这就是工程师思维的本质。

工程师思维不是多会写语法，不是把代码写得多漂亮，而是你会不会：

- 把模糊需求翻译成清晰约束。
- 把一次性产出放进可验证的流程。
- 把状态变化、异常路径、依赖关系提前设计出来。
- 把失败和回滚当成默认场景，而不是意外事件。
- 把“交付责任”扛到系统层，而不是留给下一次运气。

对 AI 一人公司来说，这种思维比过去任何时候都更重要。因为你没有完整团队给你兜底，你自己就是产品、研发、测试、运维和项目经理的最小集合。你能不能让几个 agent 在一个仓库、几份文档、几条规则里协同出稳定结果，直接决定了你能不能从“做得出来”走到“持续赚钱”。

所以，AI 一人公司真正的护城河，不是“我会用最强的模型”，而是“我有一套让 agent 长期稳定交付的微型研发体系”。

## 为什么这件事现在必须讲清楚

因为现在关于 AI 编程最流行的叙事，正在制造一种危险幻觉：好像只要模型继续变强，工程问题就会自动消失。

不会。

模型越强，你越需要工程系统。不是因为 AI 不够好，而是因为一旦它能承担更多工作，你就更需要约束它、验证它、记录它、回滚它。能力越大，外层系统越重要。

这也是我对 `Harness Engineering` 最大的判断：

它不是反 AI，也不是反 `vibe coding`。它是把 `vibe coding` 从“好玩”推进到“能交付”，从“能做 demo”推进到“能做业务”，从“个人感觉很强”推进到“结果真的可复用”。

我们不是在告别 `vibe coding`，我们是在把它升级成真正能承担商业结果的东西。

## 最后一句

如果只想做一个能跑的 demo，`vibe coding` 可能已经足够了。

但如果你想做的是一个真正要面对用户、面对交付、面对复购、面对责任的产品，那你迟早会走到 `Harness Engineering` 这一步。

因为 AI 一人公司的终局，从来不是“谁更会写 prompt”，而是“谁更早把个人 + agent 组织成一条可交付的工程流水线”。

这才是 2026 年之后，`vibe coding` 真正被重构的地方。
